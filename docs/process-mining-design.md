# 대화 기록 프로세스 마이닝 설계 (pilot)

상태: 1·2단계, 관리 화면(3단계), 개선 고리(4단계) 구현. 운영에서 돌려 본 적은 아직 없다. 5개 관점(방법론, 코드 적합성, 보안·개인정보, 운영·신뢰성, 덜어내기)의 리뷰를 반영했다 (14절).

숫자는 모두 초깃값이다. 운영 대화는 개발기에 없어서, 품질에 관한 판단은 추정이고 운영에서 돌려 봐야 확인된다.

## 1. 목적

사용자들이 gateway로 어떤 작업을 어떤 순서로 하는지를, 사람이 손대지 않아도 계속 갱신되는 목록으로 얻는다.

- 작업 유형(라벨)이 자동으로 생기고, 겹치는 것은 자동으로 합쳐진다.
- 작업 유형마다 대표 흐름(단계 목록)이 있다.
- 새 작업 유형이 나타나면 관리 화면에 드러난다.
- 언제 실행됐고 무엇을 읽었는지가 이력으로 남고, 사람이 작업 유형을 고칠 수 있다.

결과물은 사람이 읽고 판단하는 목록이다 (관리 화면 "프로세스 마이닝"). 정확한 통계가 아니다.

이번 범위에 없는 것: 흐름 변화 감지, 완료율 (11절).

## 2. 배경과 전제

### 데이터 원천

- `sessions` 테이블 (`gateway.db`): 세션별 사용자(`principal`), 현재 leaf, 생성·마지막 활동 시각.
- pi JSONL (`session_file`): 사용자 메시지, assistant 메시지(도구 호출 이름·인자), 도구 결과(`isError`, `details`), 엔트리별 id와 시각.
- 실패·중단된 턴과 버려진 분기는 commit된 leaf 경로에 없다. compaction 뒤에도 이전 메시지는 경로에 남는다.

### 도구 이름으로는 작업이 보이지 않는다

운영에서 많이 불리는 도구는 `hex-ssh`, `bash`, `read`, `repo/read_file`, `repo/edit_file`, `browser/click` 같은 범용 도구다. 도구 이름의 순서로 흐름을 그리면 어떤 작업이든 "읽기 → 수정 → 실행"이 된다.

작업의 의미는 사용자 요청과 도구 인자(어느 서버, 어느 repo, 어떤 명령)에 있다. 그래서 LLM이 세션을 읽고 추상화한다. 인자를 지나치게 줄이거나 일반화하면 이 전제가 무너진다 (5.2, 5.3).

### 환경

- LLM은 사내 vLLM이고, 보통 모델마다 서버가 하나씩 등록된다.
- gateway는 도구에 `strict`를 보내지 않는다 (`supportsStrictMode: false`). 도구 인자의 스키마 강제는 vLLM의 `--tool-strict-level parameter` 설정에 달려 있다 (`docs/OPERATIONS.md`).
- 대화 기록 보관 기간의 기본값은 "지우지 않음"이다.

## 3. 용어

| 용어 | 뜻 |
|---|---|
| 에피소드 | 한 세션 안에서 하나의 목표를 향한 연속 구간. 분석 단위 |
| 라벨 | 작업 유형. 이름과 포함 기준을 가진다 |
| 프로세스 | 라벨 + 대표 흐름 |
| 배정 전 | 아직 라벨을 붙여 보지 않은 에피소드 |
| 미분류 | 붙여 봤지만 맞는 라벨이 없던 에피소드. 새 라벨의 재료 |

## 4. 전체 흐름

핵심 결정: **세션 원문은 한 번만 읽어 에피소드 요약으로 바꾸고, 라벨에 관한 모든 일은 그 요약 위에서 반복한다.**

```
[관리 화면의 "지금 실행" 또는 매일 정한 시각, 최대 3시간 (추출은 2시간 30분까지)]
 선택 → 압축·마스킹 → ①추출 → ②배정 ─┬→ 라벨에 배정
 (결정적)  (결정적)    (LLM)   (LLM)   ├→ 미분류 (가까운 라벨이 있었으면 적어 둔다)
                          ▲            │ 20건 이상 쌓이면
                          │       ③발견(LLM) → 새 라벨
                          │            │ 라벨이 생겼으면
                          │       ④병합(LLM) → 겹치는 라벨 합침
                          ├────────────┘ 새 라벨로 다시 붙이고 또 찾는다 (한 실행에 3번까지)
                          │       ⑤검토(LLM) → 근거가 쌓인 라벨을 그대로 두거나, 고치거나, 나눈다
                          └────────────┘ 바뀐 라벨의 에피소드를 새 기준으로 다시 붙인다
                                  ⑥흐름 합성(LLM) → 대표 흐름
                                  실행 결과와 라벨 변경을 이력에 기록
```

개선 고리: 배정이 남긴 근거(늘어난 에피소드, 가까웠지만 붙지 않은 미분류)가 검토를 부르고, 검토가 라벨을 바꾸면 그 에피소드를 다시 붙여 새 근거를 만든다. 무엇이 왜 바뀌었는지는 변경 이력에 남는다.

## 5. 단계별 설계

### 5.1 선택

- 대상: 마지막 활동이 최근 30일 안이고 30분 이상 지났으며, `sessions.leaf_id`가 커서와 다른 세션.
- 순서: 최근 것부터. 시작 후 3시간이 지나면 새 LLM 호출을 보내지 않는다.
- 커서: 세션별로 "분석을 마친 마지막 엔트리 id" 하나.
- 경로: `sessions.leaf_id`에서 `parentId`를 따라 올라가 엔트리 목록(id·종류·시각·메시지)을 얻는다. `transcript.ts`의 경로 탐색을 엔트리를 돌려주는 함수로 나누고 `readTranscript`도 그것을 쓴다.

| 경우 | 처리 |
|---|---|
| 커서 엔트리가 경로 위에 있다 | 그 뒤의 엔트리만 새 부분으로 본다 |
| 커서 엔트리가 경로에 없다 (메시지 수정·재생성으로 분기) | 그 세션의 에피소드를 지우고 처음부터 다시 추출한다 |
| 새 부분에 메시지가 없다 (수동 compaction) | 커서만 옮긴다 |
| JSONL이 없다 (읽는 사이 지워짐) | 건너뛴다 |
| `sessions`에서 사라진 세션 | 에피소드와 커서를 지운다 |

턴 번호와 `session_turns`는 쓰지 않는다. 턴과 사용자 메시지가 일치하지 않는 경우(compaction 턴, 질문에 대한 답, 턴 도중 입력, 예전 세션)를 따로 다룰 필요가 없어진다.

### 5.2 압축과 마스킹 (LLM 전, 고정 규칙)

| 대상 | 처리 |
|---|---|
| 사용자 메시지 | 앞 500자, 번호를 붙인다. 질문에 대한 답(`User responded: …`)도 사용자 메시지다 |
| assistant 텍스트 | 버린다 |
| 도구 호출 | `이름(인자 앞 300자)` |
| `mcp_call` | 이름은 결과의 `details.server`/`details.tool`. 없으면 인자의 `name`. 인자는 안쪽 `arguments`를 자른다 |
| SKILL.md 읽기 (모델이 skill을 씀) | `skill/<디렉토리 이름>` |
| `<skill name="…">…</skill>`로 시작하는 사용자 메시지 (`/skill:이름`으로 부름) | 블록을 `skill/<이름>` 한 줄로 바꾸고, 그 뒤의 글을 500자까지 남긴다 |
| `StructuredOutput`, `AskUserQuestion` | 줄에서 뺀다 |
| 도구 결과 | 내용은 버린다. `isError`인 호출은 뺀다 |
| 같은 도구 연속 호출 | 인자가 같으면 `×N`으로 접는다. 다르면 고르게 5개까지 남기고 나머지는 개수만 적는다 |
| 하위 agent 내부 | 보지 않는다. `Agent` 호출 한 줄로 남는다 |
| 도구 호출이 하나도 없는 새 부분 | 추출하지 않고 커서만 옮긴다 |

- **마스킹**: 함수 하나가 비밀 모양을 `[MASKED]`로 바꾼다. 대상은 private key 블록, `Bearer`/`Basic` 뒤의 값, 이름이 password·token·secret·api_key 등인 `이름=값`, URL의 `user:pass@`, 32자 이상의 hex/base64. LLM에 넣기 전 입력과, LLM이 낸 문장을 저장하기 전에 건다.
- **크기**: 호출 하나의 입력은 12,000자까지. 사용자 메시지 경계에서 자른다. 한 구간이 그보다 길면 도구 줄의 가운데를 버린다.

### 5.3 ① 추출 (LLM)

- 입력: 이 세션의 경로 위 마지막 에피소드(목표·단계) + 압축한 새 부분.
- 출력: 에피소드 목록. 항목마다
  - 직전 에피소드의 연속인지
  - 시작·끝 사용자 메시지 번호
  - 목표 한 문장
  - 단계 1~7개 (짧은 동사구)
- 지시
  - 사용자가 새 목표를 말할 때만 자른다. 애매하면 자르지 않는다.
  - 사람 이름·값·IP·비밀은 쓰지 않는다. 시스템·repo·서비스 이름과 명령 종류는 남긴다.
- 연속이면 기존 행을 덮어쓰고 "배정 전"으로 되돌린다. 한 작업이 두 번 세어지지 않는다.
- 조각마다 에피소드 저장과 커서 이동을 한 트랜잭션으로 한다.

추출은 라벨 목록과 무관하다. 라벨 체계가 바뀌어도 원문을 다시 읽지 않는다.

### 5.4 ② 배정 (LLM)

- 대상: 배정 전 에피소드. 한 호출에 1건.
- 입력: 라벨 목록(id·이름·포함 기준) + 에피소드의 목표·단계. 라벨 목록이 프롬프트 앞에 고정되어 vLLM prefix cache가 재사용된다.
- 출력: 라벨 id와 "맞음/애매함", 또는 "없음".
- "애매함"과 "없음"은 둘 다 미분류가 된다. 목록을 주면 모델은 가장 가까운 것을 고르는 경향이 있어서, 의심을 표현할 중간 답을 준다.
- "애매함"이면 그 라벨을 에피소드에 적어 둔다 (`near_label_id`). 한 라벨에 쌓이면 ⑤ 검토가 그 기준을 다시 본다.
- 라벨이 0개면 호출 없이 전부 미분류로 둔다. 첫 실행이 이 경우다.

### 5.5 ③ 발견 (LLM)

- 트리거: 최근 30일의 미분류가 20건 이상.
- 입력: 그 미분류에서 무작위로 뽑은 최대 60건 + 기존 라벨의 이름·기준 (같은 뜻의 라벨을 만들지 않게).
- 출력: 묶음 목록 (이름, 포함 기준, 에피소드 id).
- 지시: 기본은 "묶지 않음"이다. 분명히 같은 작업만 묶는다.
- 채택 조건 (코드로 검사)
  - 에피소드 5건 이상
  - 서로 다른 사용자 2명 이상 (`sessions`와 맞춰서 센다)
  - 이름(60자)·기준(300자)이 길이 안이고 URL, 백틱, 마크업 기호(`<>[]|#*`)가 없다. 줄바꿈은 공백으로 바꾼다
- 채택되면 라벨을 만들고 그 에피소드를 배정한다. 라벨이 하나라도 생기면 남은 미분류를 "배정 전"으로 되돌린다.
- 되풀이: 같은 실행에서 ②가 새 라벨로 다시 붙이고, 남은 미분류가 20건 이상이면 ③을 또 한다. 새 라벨이 안 생기면 멈추고, 한 실행에 3번까지 한다.

### 5.6 ④ 병합 (LLM)

- 트리거: 이번 실행에서 라벨이 생겼을 때 1회.
- 입력: 활성 라벨 전체 (이름·기준·건수). 새 라벨은 표시한다.
- 질문: 새 라벨 각각이 기존 라벨 중 하나와 같은 작업인가.
- 출력: (새 라벨 id → 기존 라벨 id) 목록.
- 적용: 새 라벨에 "합쳐짐"을 표시하고 그 에피소드의 라벨을 기존 것으로 바꾼다. 한 트랜잭션. 기존 라벨의 이름과 기준은 그대로다.
- 없는 id가 하나라도 있으면 응답 전체를 버린다.
- 기존 라벨끼리는 합치지 않는다. 겹치는 라벨은 새 라벨이 생길 때만 생긴다.

### 5.7 ⑤ 검토 (LLM)

발굴한 라벨을 쌓인 근거로 다시 본다. 라벨마다 1회 호출.

- 트리거: 에피소드가 지난 검토 때보다 10건 이상 늘었거나, 그 라벨에 가까웠던 미분류가 5건 이상 쌓였다. 근거가 많은 라벨부터 한 실행에 5개까지.
- 입력: 그 라벨의 이름·기준, 다른 라벨의 이름·기준, 배정된 최근 에피소드 최대 30건, 가까웠던 미분류 최대 15건.
- 출력: 결정(그대로 / 고침 / 나눔)과 이유 한 문장. 고침이면 새 이름·기준, 나눔이면 부분들(이름, 기준, 에피소드 번호).
- 고침: 이름·기준을 바꾸고, 그 라벨의 최근 30일 에피소드와 가까웠던 미분류를 "배정 전"으로 되돌린다. 이어지는 ②가 새 기준으로 다시 붙인다. 기준이 좁아졌으면 맞지 않는 것이 빠지고, 넓어졌으면 가까웠던 것이 들어온다.
- 나눔: 부분마다 발견과 같은 채택 조건(5건 이상, 사용자 2명 이상, 글 검사)을 본다. 조건을 채운 부분이 둘 이상일 때만 나눈다. 부분을 새 라벨로 만들고 원래 라벨은 없앤다. 어느 부분에도 들지 않은 에피소드는 "배정 전"으로 돌아간다.
- 그대로 (또는 쓸 수 없는 답): 검토한 것으로만 적고, 가까웠던 미분류의 표시를 지운다. 같은 근거로 다음 실행에 다시 묻지 않는다.
- 사람이 이름·기준을 고친 라벨은 검토하지 않는다.
- 모든 변경은 한 트랜잭션이고 변경 이력에 남는다 (5.9절).

### 5.8 ⑥ 흐름 합성 (LLM)

- 트리거: 라벨에 대표 흐름이 없거나, 에피소드가 지난 합성 때보다 10건 이상 늘었을 때.
- 입력: 그 라벨의 최근 에피소드 최대 30건의 단계.
- 출력: 주 흐름 (단계 3~8개).

### 5.9 관리 화면

보고서 파일은 없다. 관리 화면 "프로세스 마이닝"이 `mining.db`를 그때그때 읽어 보여 준다 (`apps/gateway/src/admin/routes-mining.ts`).

- 실행: "지금 실행", 매일 자동 실행 시각, 동시 호출 수, 실행 이력(요청 시각, 계기, 결과, 걸린 시간, 읽은·실패한·남은 세션 수, 작업 수, 모델 또는 실패 이유). 끝까지 가지 못한 실행에는 멈춘 단계가 나온다. 이력은 10건씩 페이지로 넘겨 처음 실행까지 본다.
- 진행 상황: 실행 중에는 어느 단계인지(세션 읽기 → 프로세스에 붙이고 찾기 → 프로세스 검토 → 대표 흐름 쓰기), 그 단계에서 몇 건 중 몇 건을 했는지, 지금까지 읽은·읽지 못한·남은 세션 수와 작업 수, 마지막으로 진행한 때가 나온다. 실행이 단계가 바뀌거나 한 건을 마칠 때마다 `runs`의 자기 행에 적고, 화면은 실행 중일 때 3초마다 다시 읽는다. 5분 넘게 진행이 없으면 색으로 알린다 (LLM 호출 하나는 길어야 4분이다). 지금 LLM에 보내 둔 호출이 무엇을 다루는지도 나온다: 읽는 세션(사용자와 세션 id), 붙이는 작업(목표), 검토하거나 흐름을 쓰는 프로세스(이름). 실행은 id만 적고 gateway가 이름으로 푼다.
- 실행하기 전: 지금 실행하면 읽을 세션 수(실행과 같은 기준으로 센다)와 프로세스에 붙여 볼 작업 수가 나온다.
- 중지: 실행 중에 누르면 `runs`에 표시만 하고, 실행이 다음 LLM 호출 앞에서 보고 멈춘다 (이력에 "중지함"). 보내 둔 호출은 마치고, 그때까지 읽은 것은 남고, 라벨 단계는 하지 않는다. 아직 시작하지 않은 요청은 바로 닫는다.
- 동시 호출 수 (1~16, 처음에는 1): 세션 읽기, 배정, 대표 흐름 쓰기를 이 수만큼 한꺼번에 한다. 한 세션 안의 묶음은 앞 에피소드를 이어 가야 해서 차례로 하고, 검토는 라벨을 바꾸므로 차례로 한다. 실행을 시작할 때 읽으므로 다음 실행부터 적용된다.
- 프로세스: 건수(7일/30일/전체), 사용자 수, 생긴 때, 미분류율. 하나를 열면 기준, 대표 흐름, 그 프로세스의 변경 이력, 그 작업이 나온다.
- 변경 이력: 프로세스가 생기고, 고쳐지고, 나뉘고, 합쳐지고, 지워진 기록. 자동(어느 실행)인지 사람인지, 바뀌기 전과 뒤, 자동 검토가 적은 이유가 나온다. 10건씩 페이지로 넘기고, 프로세스를 열면 그 프로세스의 것만 나온다. 실행 이력에는 그 실행이 한 변경 수가 나온다.
- 작업: 사용자로 걸러 본다 (20건씩 페이지로 넘긴다). 프로세스별 건수가 같이 나오고, 작업을 누르면 단계와 그 대화로 가는 링크가 나온다.
- 프로세스 수정 (사람): 이름·기준 고치기, 다른 프로세스로 합치기, 지우기.
  - 이름·기준은 이후의 배정 프롬프트에 들어가므로 LLM이 지은 것과 같은 검사를 거친다 (길이, 링크·마크업 금지).
  - 지우면 그 작업은 "배정 전"으로 돌아가 다음 실행이 다시 붙여 본다. 같은 작업이 계속 쌓이면 발견 단계가 비슷한 프로세스를 다시 만들 수 있다.
  - 사람이 이름·기준을 고친 프로세스는 표시해 두고(`edited_at`), ⑤ 검토가 건드리지 않는다. 사람이 고친 것은 그대로 남는다.
  - 실행 중에는 고칠 수 없다 (409). 실행은 프로세스 목록을 읽어 둔 채로 LLM을 부르기 때문이다.

LLM이 만든 문자열은 화면에서 글자 그대로 그린다 (HTML이나 Markdown으로 풀지 않는다).

## 6. 저장 구조

`mining.db` (SQLite). gateway DB와 분리해서, pilot을 접을 때 볼륨만 지우면 된다.

| 테이블 | 컬럼 |
|---|---|
| `session_cursor` | 세션 id, 마지막으로 분석한 엔트리 id |
| `episodes` | id, 세션 id, 시작·끝 엔트리 id, 시작·끝 시각, 목표, 단계, 라벨 id, 배정한 시각, 가까웠던 라벨 id |
| `labels` | id, 이름, 포함 기준, 만든 시각, 합쳐진 대상, 합쳐진 시각, 대표 흐름, 합성 때의 건수, 검토 때의 건수, 사람이 고친 때 |
| `runs` | id, 계기(수동/자동), 요청·시작·끝 시각, 상태, 읽은·실패한·남은 세션 수, 작업 수, 모델, 실패 이유, 지금 단계와 그 단계의 마친 수·할 수, 지금 보낸 호출이 다루는 것(id), 마지막으로 진행한 때, 중지 요청 |
| `label_revisions` | 때, 실행 id(사람이면 없음), 라벨 id, 종류(생김·고침·나뉨·합쳐짐·지워짐), 그때의 이름, 전·후, 이유 |
| `settings` | 매일 자동 실행 시각 (UTC `HH:MM`), 동시 호출 수 |

- 상태 컬럼은 없다. 라벨 id와 배정 시각이 둘 다 비면 "배정 전", 배정 시각만 있으면 "미분류"다.
- 사용자 컬럼은 없다. 사용자 수를 세거나 사용자별로 볼 때는 gateway가 `sessions`에서 세션 id로 찾는다.
- 보관 기간으로 세션이 지워지면 다음 실행이 그 에피소드와 커서를 지운다. 
- 남는 것: 라벨의 이름·기준·대표 흐름과 변경 이력(여러 사용자의 에피소드에서 일반화한 문장. 검토의 이유도 마스킹하고 200자로 자른다), 실행 이력(숫자뿐이다).
- 건수는 `episodes`에서 센다. 보관 기간이 30일보다 짧으면 "30일 건수"는 보관 기간만큼만 센 값이다.
- `runs`의 상태는 요청됨 → 실행 중 → 완료·시간 상한·중단·중지함·실패다. 요청됐거나 실행 중인 것이 있으면 새 요청을 받지 않는다. 읽은·실패한·남은 세션 수와 작업 수는 실행 중에도 적으므로, 결과를 남기지 못하고 죽은 실행에도 그때까지의 수와 단계가 남는다.

## 7. 지표

| 지표 | 읽는 법 |
|---|---|
| 미분류율 | 높으면 라벨 체계가 실제 사용을 못 따라간다 |
| 최대 라벨 점유율 | 높으면 라벨이 뭉뚱그려졌다. 분할을 만들지 판단하는 근거 |
| 라벨 수 | 계속 늘기만 하면 채택 조건이 느슨하다 |

이 지표들은 라벨이 맞는지를 재지 못한다. 정확도는 사람이 프로세스의 작업을 읽어야만 확인된다.

## 8. LLM 호출, 실패, 비용

- 호출 방식: 도구 하나를 주고 그 도구를 지정해서 부른다. 결과 인자를 `validateToolArguments`로 검증한다. thinking은 끄고, 호출마다 120초 timeout을 둔다.
- 실패(검증 실패·오류·timeout): 한 번 재시도한다. 그래도 실패하면 그 단위를 건너뛰고 로그를 남긴다. 커서는 그대로라 다음 실행이 다시 한다.
- 연속 3번 실패하면 실행을 끝낸다 (이력에 "중단"). vLLM 장애가 여기에 걸린다. 동시에 여러 개를 부를 때는 성공이 하나도 끼지 않은 실패 3번이다.
- ③~⑥이 실패하면 그 실행에서 건너뛰고 다음 실행에 다시 한다. 적용은 각각 한 트랜잭션이라 반쯤 적용된 상태가 없다.
- 시간: 추출은 시작 뒤 2시간 30분까지만 쓰고, 라벨 단계는 3시간까지 쓴다. 읽을 세션이 밀려 추출이 제 몫을 다 써도 라벨 단계가 돈다. LLM 장애로 추출이 멈췄으면 라벨 단계도 하지 않는다.
- 중복 실행은 `runs`가 막는다: 요청됐거나 실행 중인 것이 있으면 새 요청을 만들지 않는다.
- LLM 호출 사이에 `gateway.db`의 읽기 트랜잭션을 열어 두지 않는다 (WAL checkpoint를 막지 않게). 대상 목록은 시작할 때 한 번 읽는다.

비용 (추정): 하루에 바뀐 세션이 200개, 세션당 1.5조각, 에피소드 2건이라고 가정한다.

- 추출 약 300회. 입력 토큰의 대부분을 차지한다.
- 배정 약 400회. 호출마다 짧고 앞부분이 캐시된다.
- 발견·병합·검토·합성은 합쳐 십여 회. 검토가 라벨을 고치면 그 라벨의 최근 에피소드 수만큼 배정이 더 든다.
- 소요 시간은 1~3시간으로 본다. 넘으면 3시간 상한에서 멈추고 다음 날 이어 간다.
- 야간 분석 입력이 사용자 세션의 vLLM 캐시를 밀어낼 수 있다. 시간 상한이 그 범위를 제한한다.

## 9. 보안과 개인정보

| 항목 | 내용 |
|---|---|
| 전송 | 기본 모델의 서버로 보낸다. 서버가 여러 대면, 그 세션을 처리하지 않은 사내 서버가 대화를 받는다 |
| 기록의 가림 범위 | `sandbox_env` 값은 도구 결과에서만 가려진다. 사용자 메시지와 도구 인자는 원문 그대로 JSONL에 있다 |
| 비밀 | 5.2의 마스킹을 입력과 출력 양쪽에 건다. 로그에는 원문을 찍지 않는다 |
| 격리 | 전용 compose 서비스로 돌린다 (10절). 비밀 없음, `edge` 네트워크만, `/data` 읽기 전용. gateway는 결과 볼륨에 실행 요청, 자동 실행 시각, 라벨 수정만 쓴다 |
| 개인 추적 | `episodes`에 사용자 컬럼이 없다. 다만 관리 화면은 작업을 사용자별로 보여 준다 (요청으로 넣었다). 관리자 로그인이 있어야 보인다 |
| 프롬프트 주입 | 분석 호출에는 실행되는 도구가 없고 출력은 검증한다. 라벨 문자열 검사와 사용자 2명 조건을 두고, 화면은 글자 그대로 그린다 |
| 파일 권한 | `mining.db`를 만들기 전에 `umask 077` |
| sandbox | 결과는 sandbox에 mount되지 않는다 |

한계

- 마스킹은 모양으로 찾는다. 패턴에 걸리지 않는 비밀은 LLM 입력과 요약에 들어갈 수 있다.
- 시스템·repo·서비스 이름은 요약에 남는다. 작업을 구분하려면 필요하다.
- 사용자 두 명이 짜면 라벨을 심을 수 있다. 관리 화면에서 지운다.

## 10. 배치

- **코드**: `apps/gateway/src/mining/`에 별도 진입점 둘. `service.ts`는 늘 떠서 10초마다 요청과 자동 실행 시각을 보고, 실행할 때마다 `main.ts`를 자식 프로세스로 띄운다. pi runtime은 실행하는 동안만 메모리에 있고, 실행이 죽어도 서비스는 남아 그 실행을 "실패"로 닫는다. gateway 프로세스는 `store.ts`와 `labels.ts`의 문자열 검사만 쓴다.
- **gateway가 실행을 직접 띄우지 않는 이유**: gateway에는 컨테이너를 만들 권한이 없고, 대화 분석을 비밀을 가진 프로세스 안에서 돌리지 않는다. 그래서 gateway는 `runs`에 요청 행만 쓰고 mining 서비스가 가져간다.
- **`gateway.db` 열기**: `new Database(path, { readonly: true, fileMustExist: true })`로 직접 열고 SELECT만 쓴다. `openDatabase`, `SessionStore`, `createModelRuntime`은 쓰지 않는다. 이들은 쓰기로 열거나 `migrate`를 돌려서, 새 이미지의 miner가 아직 옛 버전인 gateway의 DB를 바꿀 수 있다.
- **LLM**: `llm_settings`의 JSON을 읽어 기본 모델(티어면 가리키는 모델)의 서버를 등록한다. `runtime.ts`의 `createRuntime`·`register`를 export해서 `testLlmModel`과 같은 방식으로 쓴다.
- **compose**: 같은 이미지를 쓰는 `mining` 서비스를 늘 띄운다. gateway도 `mining-data`를 쓰기로 mount한다 (둘 다 uid 10001).

```yaml
  mining:
    <<: *hardening
    image: pi-gateway/gateway:${PI_GATEWAY_VERSION:-latest}
    user: "10001:10001"
    command: ["node", "apps/gateway/dist/mining/service.js"]
    volumes:
      - gateway-data:/data:ro
      - mining-data:/mining
      # 사내 CA bind는 gateway와 같다
    tmpfs:
      - /tmp:size=16m
    networks:
      - edge
```

- **Dockerfile**: gateway 단계에서 `/mining`을 uid 10001 소유로 만든다 (named volume이 처음 mount될 때 소유자를 물려받는다).
- **실행**: 관리 화면의 "지금 실행"이나 매일 자동 실행 시각이 요청을 만든다. 호스트 cron은 쓰지 않는다.
- 자동 실행 시각은 그 시각을 지나는 순간에만 요청한다. 그때 서비스가 내려가 있었거나 다른 실행이 돌고 있었으면 그날은 건너뛴다 (다음 실행이 밀린 세션을 이어 읽는다).
- gateway가 떠 있을 때만 실행된다. `/data`가 읽기 전용이라, gateway가 만들어 둔 WAL 파일이 있어야 `gateway.db`가 열린다. 못 열면 그 실행은 "실패"로 남는다.
- 자동 실행 시각은 UTC로 저장하고 화면은 브라우저 시간대로 보여 준다. "7일"·"30일"은 조회한 시각 기준이다.
- 새 환경 변수는 없다. 임계값은 코드 상수고, 운영자가 바꾸는 것은 관리 화면의 자동 실행 시각뿐이다.

## 11. 미룬 것과 만들지 않는 것

관리 화면에서 필요가 보이면 만든다.

| 미룬 것 | 만드는 신호 |
|---|---|
| 흐름 변화 감지 | 대표 흐름이 쓸모 있다고 확인된다 |
| 완료율(결과 판정) | 실패가 잦은 작업을 가려내야 한다 |
| assistant 답을 입력에 넣기 | 요약이 모호해 작업이 구분되지 않는다 |
| 라벨 폐기 | 죽은 라벨이 배정을 방해한다 |
| 일별 건수 테이블 | 보관 기간이 30일보다 짧다, 또는 보관 기간보다 긴 추이를 봐야 한다 |
| 대표 흐름 변경 이력 | 흐름이 언제 어떻게 바뀌었는지 봐야 한다 |
| 기존 라벨끼리의 병합 | 검토로 넓어진 라벨들이 겹친다 |
| 지운 라벨을 다시 만들지 않기 | 사람이 지운 것이 다시 생긴다 |

만들지 않는 것: 실시간 분석, 사람이 프로세스를 새로 만드는 기능, 임베딩 기반 군집, 단계 어휘를 표준화한 빈도 그래프(directly-follows).

## 12. 구현 순서

**개발기에서 확인한 것**

- 읽기 전용 mount에서 WAL DB 열기: gateway가 떠 있는 동안과 비정상 종료 뒤에는 열리고, 쓰는 중에도 새 행이 보인다. gateway가 정상 종료된 뒤에는 `-wal`·`-shm` 파일이 없어 열리지 않는다 (`SQLITE_CANTOPEN`). 그래서 mining은 gateway가 떠 있을 때만 돈다. 못 열면 로그를 남기고 그 실행을 "실패"로 닫는다.
- 아직 안 한 것: 운영 vLLM을 상대로 한 호출.

**1단계: 추출까지 (구현함)**

- 선택, 압축·마스킹, ① 추출, `episodes` 저장. 보고서는 에피소드 목록만 낸다.
- 운영에서 확인: 요약이 작업을 서로 구분하는가. 비밀이 남는가.

**2단계: 나머지 (구현함)**

- ② 배정, ③ 발견, ④ 병합, ⑤ 흐름 합성, 보고서.
- 운영에서 확인: 라벨별 예시 목표를 사람이 읽어 라벨이 맞는지 본다.
- 1단계의 요약 품질을 운영에서 보기 전에 만들었다. 요약이 작업을 구분하지 못하면 라벨도 뭉뚱그려지므로, 처음에는 사용자별 작업부터 읽는다.
- 라벨은 미분류가 20건 이상 쌓인 실행에서 처음 생긴다 (작업이 그만큼 뽑혔으면 첫 실행일 수도 있다).

**3단계: 관리 화면 (구현함)**

- 요청: 관리 화면에서 관리하고, 무엇이 마이닝됐는지 추적할 수 있어야 한다. "지금 실행"과 사람의 라벨 수정도.
- 보고서 파일과 호스트 cron을 없애고, 실행 이력(`runs`)과 상시 서비스, 전용 페이지를 넣었다 (5.9절, 10절).
- 14절의 리뷰에서 뺀 것 중 이 요청으로 되돌린 것: 전용 페이지, 사람이 라벨을 고치는 기능. 이력은 숫자뿐인 `runs`만 넣었다.

**4단계: 개선 고리 (구현함)**

- 요청: 발굴한 프로세스를 계속 개선하고, 필요하면 더 발굴하는 고리가 있어야 한다. 전에는 라벨이 쌓이기만 하고, 한번 붙은 에피소드와 한번 지은 기준은 다시 보지 않았다.
- 넣은 것: 배정의 "애매함"을 근거로 남김, ⑤ 검토(고침·나눔), 바뀐 라벨의 재배정, 한 실행 안에서 붙이고 찾기를 되풀이, 변경 이력, 추출과 라벨 단계의 시간 분리.
- 14절의 리뷰에서 뺀 것 중 되돌린 것: 라벨 분할, `label_events`(변경 이력).
- 개발기에서 확인한 것은 동작뿐이다 (정해진 답을 주는 LLM으로 한 테스트). 모델이 실제로 좋은 결정을 내리는지, 고침과 나눔이 너무 잦지 않은지는 운영에서 변경 이력을 읽어 확인한다.

각 단계에서 결과가 쓸모없으면 거기서 멈춘다.

## 13. 운영에 물어볼 것

1. vLLM이 `--tool-strict-level parameter`로 도는가, 또는 LLM 설정의 compat에서 `supportsStrictMode`를 켰는가. 둘 다 아니면 도구 인자가 스키마와 어긋날 수 있어 재시도가 늘어난다.
2. 서비스 키로 들어오는 자동 호출의 비율. 많으면 라벨을 지배한다. `sessions`에는 출처 컬럼이 없어 지금은 가릴 수 없다.
3. 실제 사용자 수. 사용자 2명 조건 때문에, 사용자가 아주 적거나 각자 다른 일만 하면 아무것도 잡히지 않는다.
4. 보관 기간을 설정했는가.
5. 시스템·repo 이름이 요약과 관리 화면에 남는 것을 허용하는가.
